# Почему флагман

SONYA — это не просто AI-Кулинар и не одноразовая учебная форма. Архитектура строится как единый семейный assistant-layer:

```text
ФОТО / ТЕКСТ / СЕМЕЙНЫЙ КОНТЕКСТ
                 ↓
             SONYA AI
                 ↓
┌──────────────────────────────────────────────┐
│ Зрение │ Меню │ Холодильник │ Склад │ События │
│ Покупки │ Бюджет │ Тайминг │ Голос │ Подача   │
└──────────────────────────────────────────────┘
                 ↓
        РЕШЕНИЕ ПОДТВЕРЖДАЕТ ЧЕЛОВЕК
```

Ключевой принцип продукта:

```text
НАБЛЮДЕНИЕ ≠ ПРЕДПОЛОЖЕНИЕ ≠ РЕШЕНИЕ ПОЛЬЗОВАТЕЛЯ
```

СОНЯ не должна выдавать догадку модели за установленный факт и не заявляет, что заказ, оплата или бронирование реально выполнены без соответствующей интеграции и подтверждения человека.

# Мультимодальный AI

## Режим «Хочу такое»

Пользователь загружает фото готового блюда, сервировки или идеи и пишет, что хочет получить.

СОНЯ:

1. выделяет то, что действительно видно;
2. отдельно показывает предположения;
3. объясняет способ приготовления;
4. адаптирует идею под семью или событие;
5. формирует варианты меню;
6. предлагает безопасные замены;
7. собирает недостающие покупки.

## Режим «Что у меня есть»

Фото холодильника или продуктов используется как вход в другой сценарий:

```text
что видно дома
    ↓
что можно приготовить
    ↓
что уже есть
    ↓
чего не хватает
    ↓
что купить
```

# Реальный vision-тест

Один из тестов выполнялся на фото детского блюда со спагетти, сосиской, морковью и зеленью.

В процессе доработки локального контура были выявлены и исправлены типовые ошибки vision-модели:

- «картофель» вместо моркови;
- «голубая» вместо бирюзовой тарелки;
- невалидный JSON от vision-модели;
- смешивание наблюдения и предположения;
- нестабильный формат ответа.

Финальный локальный контур использует:

```text
Qwen3-VL
  ↓
resilient JSON parsing
  ↓
visual grounding / semantic validator
  ↓
RAG
  ↓
структурированный ответ SONYA
```

В ответе отдельно показываются:

- **что видно точно**;
- **что предполагается**;
- **как приготовить / что сделать**;
- **безопасность и замены**;
- **варианты для праздника**.

# Голос и режим готовки

Для сценария «руки заняты — читать неудобно» добавлена голосовая работа:

```text
AI-ответ
   ↓
ОЗВУЧИТЬ
   ↓
СОНЯ ЧИТАЕТ РЕЗУЛЬТАТ
```

Отдельный **режим готовки** позволяет проходить инструкцию пошагово:

```text
Шаг 1 → Повторить → Далее → Шаг 2 → ...
```

В интерфейсе также реализован крупный Focus Mode: фон сайта размывается, карточка открывается поверх интерфейса, а пошаговый режим показывает алгоритм приготовления наглядно и крупно.

## 3. Как была выстроена логика взаимодействия в сценарии?

Основной сценарий построен вокруг реальной бытовой задачи: пользователь видит идею блюда или содержимое холодильника и хочет быстро превратить изображение в понятный план действий.

Логика взаимодействия:

```text
1. Пользователь выбирает сценарий
   ├─ «Хочу такое»
   └─ «Что у меня есть»

2. Загружает изображение

3. Формулирует текстовый запрос

4. Добавляет контекст
   ├─ возраст ребёнка
   ├─ количество гостей
   ├─ бюджет
   ├─ образ жизни
   └─ ограничения / аллергии

5. SONYA выполняет совместный анализ
   IMAGE + TEXT + CONTEXT

6. Результат разделяется на независимые блоки
   ├─ что видно точно
   ├─ что является предположением
   ├─ что приготовить / сделать
   ├─ безопасность и замены
   ├─ варианты меню
   └─ покупки

7. Пользователь может
   ├─ открыть карточку в Focus Mode
   ├─ прослушать ответ
   ├─ включить пошаговый режим готовки
   ├─ перейти к плану события
   └─ перейти к покупкам
```

Главный принцип взаимодействия — **не смешивать факт изображения, предположение модели и последующее действие пользователя**. Поэтому наблюдения и гипотезы отображаются отдельно.

## 4. С какими сложностями пришлось столкнуться и как они были обойдены?

### Нестабильность vision-ответа

Vision-модель могла корректно понять изображение, но вернуть повреждённый JSON. Первоначально это приводило к падению всего прохода.

Решение: вместо одного жёсткого парсера был сделан устойчивый pipeline:

```text
strict JSON
   ↓
loose repair
   ↓
broken JSON salvage
   ↓
text fallback
   ↓
semantic reconstruction
```

Одна ошибка синтаксиса больше не должна обрушать весь пользовательский сценарий.

### Ошибки классификации похожих объектов и цветов

На тестовом изображении модель путала морковь с картофелем и неточно называла оттенок тарелки.

Решение:

- физические признаки отделены от продуктовой интерпретации;
- добавлены правила visual grounding;
- введена нормализация цвета;
- добавлен semantic validator;
- подготовлена база для regression-cases и confusion matrix.

### Смешивание фактов и предположений

Модель могла написать «сосиска» или «укроп» как установленный факт, хотя по изображению корректнее сначала фиксировать форму и цвет.

Решение: ответ разделён на:

```text
OBSERVATION
ASSUMPTION
ACTION
```

Например:

- факт: «круглые розовые ломтики»;
- предположение: «вероятно сосиска».

### Стабильность UI при разном объёме ответа

Разные ответы модели имеют разную длину. Это приводило к слишком высоким карточкам и ухудшению читаемости.

Решение:

- карточная структура;
- адаптивная сетка;
- крупный Focus Mode поверх интерфейса;
- размытие фонового сайта;
- увеличенный текст;
- отдельный полноэкранный режим пошагового алгоритма.

### Длительное локальное vision-inference

Локальная Qwen3-VL значительно тяжелее обычного текстового ответа.

Решение:

- профиль `FAST`;
- один vision-проход;
- детерминированная сборка там, где второй LLM не нужен;
- уменьшение изображения перед отправкой;
- Agent Trace для измерения фактического времени каждого этапа.

### Предсказуемость интерфейса

AI может возвращать нестабильные формулировки, но UI должен оставаться одинаковым.

Решение: backend приводит результат к фиксированной структуре:

```text
observation[]
assumptions[]
preparation[]
safety[]
menu[]
shoppingList[]
```

Frontend работает уже с этим контрактом, а не с произвольным текстом модели.

# SONYA Meal / Event Planner · следующий продуктовый слой

Следующая версия развивает текущий MVP до семейного планировщика питания и событий.

## До 10 фотографий блюд

Каждое фото становится отдельной позицией:

```text
Фото → распознавание → название → состав → порции → время → выбрать ☑
```

Пользователь выбирает несколько блюд, после чего SONYA формирует итоговое меню.

## Холодильник + домашний склад

Остатки должны храниться количественно:

| Продукт | Остаток | Ед. |
|---|---:|---|
| яйца | 11 | шт |
| мука | 2300 | г |
| сахар | 1250 | г |
| масло сливочное | 180 | г |
| масло растительное | 650 | мл |
| рис | 900 | г |

Нормализация единиц:

```text
1 кг = 1000 г
1 л  = 1000 мл
```

Расчёт закупки:

```text
НУЖНО ДЛЯ МЕНЮ
      −
ЕСТЬ ДОМА
      =
ДОКУПИТЬ
```

## Общая корзина

Будущая логика:

```text
выбранные блюда
      ↓
объединить одинаковые ингредиенты
      ↓
вычесть домашние остатки
      ↓
пересчитать в упаковки
      ↓
оценить стоимость + доставку
      ↓
показать варианты магазинов
```

Пока реальная покупка не интегрирована, UI явно должен маркировать такой заказ как `DEMO / сформирован`, а не как фактически отправленный в магазин.

# Kitchen Runbook · технологический процесс

Целевая функция SONYA — не просто рецепт, а **план производства блюда / меню во времени**.

Пример:

```text
10:00  заготовки
10:20  овощи / декор
12:00  холодные позиции
13:30  горячий цех
14:20  сервировка
15:00  гости
15:20  подача горячего
16:15  десерт / торт
```

SONYA должна учитывать:

- что можно приготовить заранее;
- что нельзя готовить слишком рано;
- какие процессы идут параллельно;
- что хранится холодным;
- что должно подаваться горячим;
- сколько времени займёт работа одному или двум людям;
- последовательность подачи как в ресторанной кухне.
